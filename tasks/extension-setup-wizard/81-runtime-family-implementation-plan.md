# Extension Host Runtime Family — Implementation Plan

> **Superseded boundary:** D043 established that `ExtensionManager` and the
> implementation/lifecycle binding of `ExtensionBase` belong to the Host
> Runtime, while Core owns the extension-table schema and implements Runtime
> ports. This document remains evidence for package/native-consumer work but is
> not the current implementation authority until revised.

## Objective

Move the native Extension Runtime implementations into independently released,
Peer-type-specific packages owned by `ext-reg`, then make Core and Client consume
those packages and delete their embedded duplicates. The first functional
correction is Python local-first activation: exact locally installed wheel
presence wins before any Registry access.

## Impact Handshake

- **Invariant changed**: Core activation no longer resolves a Registry Release
  when an exact compatible Distribution is locally present.
- **Database unchanged**: an `extensions` row remains deployment-installed
  truth; `enabled[]` remains Peer intent; no `present` or runtime state is added.
- **Authorities preserved**: Registry owns Releases/Distribution hosting;
  Toolkit owns developer build/admission workflows; Peer repositories own
  database, delegation, publication and UI; Runtime packages own native
  consumer behavior, and only the Web member owns its structural module
  lifecycle.
- **Compatibility identity preserved**: Python associations still target
  `core-py` and its Core version; MF associations still target `@inkcre/core`.
  Runtime package versions do not replace Host SDK versions.
- **No generic revival**: historical target/digest/condition APIs remain
  retired.
- **Delivery effect**: two new Runtime release assets and one Toolkit minor
  release precede Core/Client adoption. Registry production deployment is not
  required for PR preview acceptance.

## Installed Wheel Metadata Contract

Every Core Python Extension wheel carries
`<project>-<version>.dist-info/inkcre-extension.json`:

```json
{
  "schema_version": 1,
  "name": "inkcre/twitter",
  "version": "0.2.1",
  "host_sdk": {
    "name": "core-py",
    "version": ">=0.1.1 <0.2.0"
  },
  "python": {
    "project": "inkcre-ext-twitter",
    "project_version": "0.2.1",
    "entry_point": {
      "group": "inkcre.core.extensions",
      "name": "twitter",
      "object": "extensions.twitter:Extension"
    }
  }
}
```

Rules:

- `name` and `version` are the canonical Extension Release identity;
- project/version must equal wheel filename and Core Metadata after the existing
  lossless SemVer→PEP 440 mapping;
- Host SDK and entry point must equal `[tool.inkcre-extension]` and standard
  `entry_points.txt`;
- the file contains no Peer, database, target, digest, provenance, config,
  state, enabled or present fields;
- Runtime reads it with `importlib.metadata.Distribution.read_text()` and then
  verifies standard Distribution metadata/entry points/files;
- discovery first selects the record matching the Extension name/version, then
  derives its normalized Python project identity;
- exactly one installed Distribution may own that project identity, and that
  Distribution must satisfy the complete record. A second or malformed owner
  is an ambiguity error rather than something discovery silently ignores.

The Wheel and installed-project specifications permit additional
installer-specific `.dist-info` files. Toolkit uses the pinned `wheel` tool's
supported unpack/pack path so `RECORD` is regenerated by the reference tooling;
it does not hand-write archive hashes.

Add generated `contracts/python-installed-extension.schema.json`. Toolkit owns
the source Pydantic model and generation. Registry admission and the Python
Runtime each validate against the same field semantics; the Runtime does not
take a production dependency on the Developer Toolkit.

## Core Python Runtime API

The public semantic API is:

```python
runtime = CorePythonExtensionRuntime(
    host_sdk=HostSDK(name="core-py", version=core_version),
)

release = runtime.resolve_install(
    ExtensionSelection(name="inkcre/twitter", version="0.2.1"),
    registry_origin=operation_registry_origin,
)
# Core uses this result when creating or changing the deployment-installed row.

prepared = runtime.prepare_installed(
    ExtensionSelection(name="inkcre/twitter", version="0.2.1"),
    registry_origin=lambda: resolve_operation_registry_origin(),
)

loaded = runtime.load(prepared)
# Core validates ExtensionBase and owns on_start/on_close, publication,
# RuntimeClaim and compensation.
runtime.unload(loaded)
```

`resolve_install()` is the explicit Registry-authorized path for creating or
changing deployment-installed truth. `prepare_installed()` is
synchronous/native-consumer work and may be called through Core's existing
thread boundary. Its Registry-origin provider is lazy: Core does not resolve or
validate Registry configuration before local discovery. Its fixed sequence is:

1. inspect installed Distributions for an exact valid installed metadata record;
2. on exact hit, return `PreparedPythonExtension` without constructing a
   Registry client or making network requests;
3. on absence, invoke the Registry-origin provider exactly once, then resolve
   the exact native Release and Python association;
4. enforce published/yanked policy appropriate to installed restore;
5. use Registry Simple/pip to acquire, then rediscover the installed record;
6. return the exact prepared Distribution or a typed Runtime error.

It does not refresh yanking/block state on an exact local hit. Version change
and deployment install call `resolve_install()` rather than smuggling a
different policy into activation.

`load()` owns entry-point load, module-origin validation and reversible module
ownership only. Core receives the loaded candidate, validates that it is the
expected `ExtensionBase`, and retains the complete Extension lifecycle:
instance construction, RuntimeClaim, config/state access,
`on_start`/`on_close`, FastAPI/Source/Resolver/Peer publication, rollback and
shutdown compensation. `unload()` only releases module ownership after Core has
completed that lifecycle. The Runtime imports no `app.*` module and receives
Host SDK identity/version from Core.

The current pip safety posture remains part of the Runtime extraction. Local
discovery is read-only. Before mutation, dependency planning must continue to
reject replacement of Core-owned or already-loaded distributions. Once pip has
started mutating the active interpreter, an incomplete acquisition or a
replacement that cannot be safely observed in-process raises the existing
restart-required class of error; extraction must not weaken this into a normal
retry.

## Client Web Runtime API

The Web package exposes:

```ts
interface ModuleFederationPort {
  registerRemotes(remotes: readonly RemoteConfig[], options: { force: true }): void
  loadRemote(name: string): Promise<unknown>
}

const runtime = new ClientWebExtensionRuntime({
  hostSdk: { name: '@inkcre/core', version: coreVersion },
  moduleFederation,
  fetch,
})

const prepared = await runtime.prepare({ name, version, registryOrigin, policy })
const handle = await runtime.activate(prepared)
await runtime.deactivate(handle)
```

The package owns exact Release/MF parsing, SDK precheck, remote registration and
load, the four structural lifecycle hooks
`initialize/activate/deactivate/dispose`, compensation, module handle and
volatile error state. The loaded module is structural data to this package; it
does not import Vue or define the Client Host SDK's setup-contribution type. It
depends on a structural MF port, not a concrete MF runtime package.

Client retains `WebExtensionHost` as the deployment-state coordinator: it
resolves Registry-origin policy, sequences runtime and enabled persistence,
performs persistence compensation, selects/delegates Peers, and projects the
loaded `@inkcre/core` Extension module into the Client-owned Vue setup
contribution shown by the popup shell. Web does not implement Python local
wheel presence.

## Implementation Batches

### Batch A — ext-reg contract and Toolkit `0.2.0`

Owned repository: `ext-reg`.

1. Add the installed-wheel Pydantic model and generated JSON Schema.
2. Extend Toolkit's Python wheel inspector to require exact installed metadata.
3. Add one Toolkit Python wheel finalize command that:
   - reads `[tool.inkcre-extension]` and standard project/entry-point metadata;
   - accepts one already-built wheel and an empty output directory;
   - uses a temporary directory plus pinned `wheel unpack`/`wheel pack` to add
     `inkcre-extension.json` and regenerate `RECORD`;
   - publishes the finalized wheel only after repack and structural inspection
     succeed, and removes temporary output on failure.
   Producer repositories continue to invoke their normal PEP 517 build backend;
   Toolkit does not become a build-system compatibility layer. The Toolkit CLI
   extra pins `wheel>=0.47,<0.48` for this supported path.
   The command is:

   ```text
   inkcre-ext python wheel finalize \
     --project <producer-pyproject.toml> \
     --wheel <input.whl> \
     --output-dir <empty-directory>
   ```
4. Make Registry Python admission require and compare the installed record with
   the prepared Python association.
5. Keep preview inventory and MF behavior unchanged.
6. Run existing ext-reg contracts plus focused metadata/inspector evidence; do
   not add artifact-wide or public-byte verification.

## Explicit Non-goals

- no database `present` or `running` field;
- no `extension_peer_bindings` resurrection;
- no shared Python/Web lifecycle state machine;
- no generic target, condition, capability digest or artifact manifest;
- no backward-compatibility shim for historical `@inkcre/extension-runtime`;
- no Runtime ownership of Peer delegation, PostgREST, FastAPI publication
  implementation, setup wizard, Source/Cron/Job or application UI;
- no production Registry deployment merely to validate PR previews;
- no full-tree public reads, byte comparison, digest identity substitution,
  cache-busters or inflated retries.
